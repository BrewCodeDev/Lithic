# LEP100-15: Multisignature Smart Account Standard

**Status:** Draft  
**Author:** J. King Kasr (KaJ Labs)  
**Category:** Standards Track  
**Language Target:** Lithic (`.lithic`)  
**VM Target:** LithoVM  
**Network:** Lithosphere  
**Standard Identifier:** LEP100-15  
**Recommended Reference Implementation:** Lithosphere Secure Contracts Library (LSCL)  
**License:** Apache-2.0  

---

## Abstract

LEP100-15 defines the canonical multisignature smart-account standard for the Lithosphere ecosystem.

A LEP100-15 account is a programmable smart account controlled by multiple authorized signers under an explicit approval threshold such as 2-of-3, 3-of-5, or 5-of-7.

The standard defines interoperable behavior for:

- native LITHO custody and transfers;
- LEP100 fungible-token custody;
- LEP100 NFT and multi-token custody;
- arbitrary Lithic/LithoVM contract calls;
- EVM-compatible calls;
- transaction proposal and approval;
- threshold-based execution;
- batched transactions;
- signer rotation;
- signature-scheme agility;
- recovery;
- timelocks;
- spending policies;
- agent delegation;
- AI-assisted transaction analysis;
- AI risk scoring;
- AI policy enforcement;
- LEP100 provenance receipts;
- optional zk-verifiable AI decisions;
- contract-signature verification;
- wallet, dApp and infrastructure interoperability.

LEP100-15 is designed to serve individual users, organizations, protocols, treasuries, DAOs, validator operators, AI agents, autonomous applications and machine-controlled infrastructure.

The primary security principle of LEP100-15 is:

> **No AI output, automation process, application or relayer may obtain authority exceeding the explicit permissions granted by the multisig account.**

AI functionality extends multisignature security and usability. It does not implicitly replace cryptographic authorization.

---

# 1. Motivation

Single-key accounts create a concentrated security dependency.

Loss, theft or compromise of one private key can result in total loss of control.

Multisignature accounts reduce this risk by distributing authority across multiple independent signers.

Lithosphere additionally requires multisignature infrastructure capable of supporting Web4 environments in which transactions may be initiated, analyzed, coordinated or executed by humans, software agents and autonomous systems.

Traditional multisig standards generally focus on:

```text
propose
   ↓
collect signatures
   ↓
execute
```

LEP100-15 expands this model to:

```text
Intent
  ↓
Proposal
  ↓
Simulation
  ↓
AI / Policy Analysis
  ↓
Signer Review
  ↓
Threshold Authorization
  ↓
Execution
  ↓
Provenance + Audit Record
```

This creates a smart-account primitive suited for both human-controlled and agentic environments.

# 3. Non-Goals

LEP100-15 does NOT:

- define a fungible token;
- redefine LEP100 asset standards;
- require AI functionality;
- require autonomous transaction execution;
- require one specific AI model;
- require one specific wallet implementation;
- make natural-language instructions authoritative;
- permit AI output to bypass signature requirements;
- require weighted voting in the base standard;
- mandate upgradeable account contracts;
- mandate any specific UI.

# 6. Core Concepts

## 6.1 Smart Account

A LEP100-15 smart account is a contract-controlled account capable of holding assets and executing transactions after its configured authorization requirements are satisfied.

---

## 6.2 Signer

A signer is an identity authorized to approve account transactions.

A signer may represent:

```text
Human private key
Hardware wallet
Contract
Institutional custody system
HSM
MPC wallet
Agent
Automation service
Recovery authority
Post-quantum key
```

---

# 7. Signer Types

The standard defines the following signer classes.

```text
KEY
CONTRACT
AGENT
RECOVERY
```

Implementations MAY add additional types.

---

## 7.1 Key Signer

Traditional cryptographic signer.

Examples:

- secp256k1;
- Ed25519;
- P-256;
- supported post-quantum algorithms.

---

## 7.2 Contract Signer

A smart contract satisfying the LEP100-15 signature-validation interface.

This permits:

- another multisig;
- DAO;
- custody contract;
- organization account;
- policy contract;

to act as a signer.

---

## 7.3 Agent Signer

A software or AI-controlled signer operating under a mandatory permission envelope.

An agent signer MUST NOT automatically receive unrestricted account authority.

---

## 7.4 Recovery Signer

A signer that participates only in specifically defined recovery operations.

Recovery signers MUST NOT automatically receive ordinary spending authority.

---

# 8. Threshold Model

The base standard uses M-of-N authorization.

Example:

```text
Owners: 5
Threshold: 3
```

means that three distinct eligible signers must authorize a transaction.

Invariant:

```text
1 <= threshold <= active_signer_count
```

An implementation MUST NOT permit a configuration that violates this invariant.

---

# 9. Account State

A compliant account SHOULD maintain at least:

```lithic
state {
    signers: mapping<SignerId, Signer>;
    signer_count: u32;
    threshold: u32;

    next_nonce: u256;

    proposals: mapping<Hash, Proposal>;
    approvals: mapping<Hash, mapping<SignerId, bool>>;
    approval_count: mapping<Hash, u32>;

    policies: mapping<Hash, Policy>;
    agent_permissions: mapping<SignerId, AgentPolicy>;

    ai_profiles: mapping<Hash, AIProfile>;
    ai_assessments: mapping<Hash, AIAssessment>;

    recovery_config: RecoveryConfig;

```

This code is normative pseudocode representing the required state model rather than a requirement for identical storage layout.

# 10. Transaction Model

## 10.1 Call

The canonical call structure is:

```lithic
struct Call {
    target: address;
    value: u256;
    data: bytes;
    operation: Operation;
}
```

Where:

```lithic
enum Operation {
    CALL,
    STATIC_CALL
}
```

`DELEGATE_CALL` SHOULD be disabled by default.

Implementations exposing delegate execution MUST identify it as an elevated-risk capability.

```lithic
    nonce: u256;

    valid_after: u64;
    valid_until: u64;

    policy_hash: bytes32;
    metadata_hash: bytes32;
```

# 12. Transaction Domain Separation

Signatures MUST be bound to:

- LEP100-15;
- standard version;
- chain ID;
- account address;
- transaction nonce;
- complete call data;
- validity period;
- policy hash.

Conceptually:

```text
DOMAIN =
    "LEP100-15"
    || VERSION
    || CHAIN_ID
    || ACCOUNT_ADDRESS
```

Transaction hash:

```text
TX_HASH = HASH(
    DOMAIN
    || NONCE
    || HASH(CALLS)
    || VALID_AFTER
    || VALID_UNTIL
    || POLICY_HASH
    || METADATA_HASH
)
```

The canonical serialization MUST be deterministic.

---

# 13. Replay Protection

Every proposed transaction MUST use a unique account nonce.

The account maintains:

```text
next_nonce
```

When a proposal is accepted:

```text
proposal.nonce = next_nonce
next_nonce += 1
```

Execution order does not need to match proposal order.

Therefore:

```text
Proposal #50
Proposal #51
Proposal #52
```

may execute:

```text
#51
#50
#52
```

provided each proposal remains valid.

A successfully executed transaction MUST NEVER execute again.

---

# 14. Proposal Lifecycle

The canonical state machine is:

```text
PROPOSED
    │
    ├── approvals < threshold
    │
    ▼
PENDING
    │
    ├── threshold reached
    ▼
READY
    │
    ├── execute
    ▼
EXECUTED
```

Alternative terminal states:

```text
CANCELLED
EXPIRED
```

---

# 15. Proposal Status

```lithic
enum ProposalStatus {
    PENDING,
    READY,
    EXECUTED,
    CANCELLED,
    EXPIRED
}
```

# 19. Signature Algorithms

The standard MUST NOT permanently couple account identity to a single cryptographic algorithm.

Example:

```lithic
enum SignatureScheme {
    SECP256K1,
    ED25519,
    P256,
    CONTRACT,
    PQ
}
```

Future algorithm identifiers MAY be registered.

This design permits cryptographic migration without changing the smart-account address.

# 21. Contract Signature Validation

LEP100-15 defines a contract-signature validator.

```lithic
interface ILEP10015SignatureValidator {

    public view fn is_valid_signature(
        digest: bytes32,
        signature: bytes
    ) -> bool;
}
```

This enables multisig nesting.

Example:

```text
Company Treasury MultiSig
       │
       ├── Founder
       ├── CFO
       └── Treasury Committee MultiSig
```

The committee multisig itself may satisfy one signer slot.

EVM adapters MAY additionally expose an EIP-1271-compatible signature interface.

---

# 22. Approval Rules

An approval MUST:

1. originate from an active eligible signer;
2. reference an existing transaction;
3. reference an unexecuted transaction;
4. reference a non-expired transaction;
5. be unique for that signer and transaction.

Duplicate approvals MUST NOT increase the approval count.

---

# 23. Revocation

A signer MAY revoke approval while:

```text
status != EXECUTED
```

and the transaction has not begun execution.

After revocation:

```text
approval_count -= 1
```

If approval count falls below the threshold:

```text
READY → PENDING
```

---

# 24. Execution

A transaction MAY execute only when:

```text
approval_count >= threshold
AND current_time >= valid_after
AND current_time <= valid_until
AND policy requirements satisfied
AND transaction has not previously executed
```

Execution MUST mark the transaction as consumed before externally calling untrusted contracts, or use an equivalent reentrancy-safe state transition.

---

# 25. Atomic Batch Transactions

LEP100-15 MUST support batching.

Example:

```text
Call 1 → Pay supplier
Call 2 → Transfer LEP100 token
Call 3 → Update protocol parameter
```

Core batch execution MUST be atomic.

If any call fails:

```text
ALL CALLS REVERT
```

Optional non-atomic batch execution MAY exist as a separately identified extension.

A treasury wants to transfer:

```text
250 LITHO
```

to:

```text
0xRecipient
```


```text
Signer A → approve
Signer B → approve
Signer C → approve
```

The transaction becomes:

```text
READY
```

and may execute.

# 29. Administrative Actions

The following actions MUST themselves require account authorization:

```text
add signer
remove signer
replace signer
change threshold
change account policy
configure recovery
change AI policy
grant agent authority
revoke agent authority
change signature verifier
authorize upgrade
```

An individual signer MUST NOT be able to perform these operations unilaterally unless the account itself is configured as 1-of-N.

---

# 30. Self-Call Administration

Administrative operations SHOULD execute through the multisig itself.

Example:

```text
target = multisig_address
method = add_signer(...)
```

This gives configuration changes the same:

- proposal;
- review;
- approval;
- audit;
- execution;

lifecycle as ordinary transactions.

---

# 31. Add Signer

```lithic
public fn add_signer(
    signer: Signer
) only_self {
    require(!signers[signer.id].active);

    signers[signer.id] = signer;
    signer_count += 1;

    emit SignerAdded(signer.id);
}
```

---

# 32. Remove Signer

```lithic
public fn remove_signer(
    signer_id: SignerId
) only_self {

    require(signers[signer_id].active);

    require(
        signer_count - 1 >= threshold
    );

    signers[signer_id].active = false;
    signer_count -= 1;

    emit SignerRemoved(signer_id);
}
```

The account MUST NOT remove a signer when doing so would produce an invalid threshold.

---

# 33. Replace Signer

Atomic signer replacement SHOULD be supported.

```lithic
public fn replace_signer(
    old_signer: SignerId,
    new_signer: Signer
) only_self;
```

This is preferable to separate remove/add transactions during key compromise.

---

# 34. Change Threshold

```lithic
public fn set_threshold(
    new_threshold: u32
) only_self {

    require(new_threshold >= 1);
    require(new_threshold <= signer_count);

    threshold = new_threshold;

    emit ThresholdChanged(new_threshold);
}
```

---

# 35. Timelocked Administration

Accounts SHOULD support configurable timelocks for high-risk administrative operations.

Example:

```text
Normal payment:
0-minute delay

Signer replacement:
12-hour delay

Threshold reduction:
48-hour delay

Contract upgrade:
72-hour delay
```

This permits signers or monitoring systems to detect hostile account reconfiguration.

# 38. AI-Native Multisig Extension

# 39. AI Security Principle

AI reasoning is not equivalent to cryptographic authorization.

Unless explicitly configured otherwise:

```text
AI recommendation != signer approval
```

A model response MUST NOT silently increase the approval count.

---

# 40. AI Primitive 1 — Transaction Explanation

Wallets MAY request an AI-generated explanation before users sign.

For example:

```text
Raw call:

0xa9059cbb000000000000000000...

AI explanation:

"This transaction transfers 50,000 USDC from the treasury
to 0x84...92 and does not grant an allowance."
```

The explanation is advisory.

The canonical encoded transaction remains authoritative.

A receipt SHOULD cryptographically bind:


# 47. AI Modes

Every account enabling AI policy MUST explicitly choose a mode.

```lithic
enum AIMode {
    ADVISORY,
    REQUIRED_REVIEW,
    POLICY_GUARD
}
```

---

## 47.1 ADVISORY

AI results are displayed but never affect execution.

```text
AI says BLOCK
        ↓
Humans can still execute with threshold
```

This SHOULD be the default.

---

## 47.2 REQUIRED_REVIEW

A valid AI assessment must exist before execution.

AI cannot approve the transaction, but analysis is mandatory.

Example:

```text
3 signatures
+
valid AI assessment
=
executable
```

---

## 47.3 POLICY_GUARD

AI output participates in a predefined deterministic policy.

Example:

```text
risk_score <= 5,000
```

If:

```text
risk_score > 5,000
```

the account may require:

```text
additional signer
timelock
human override
or cancellation
```

AI behavior MUST be defined before the transaction is proposed.

---

# 48. AI Fail Modes

AI-dependent policies MUST specify behavior when AI service is unavailable.

```lithic
enum AIFailMode {
    ADVISORY_CONTINUE,
    FAIL_CLOSED,
    HUMAN_OVERRIDE
}
```

`FAIL_CLOSED` may create availability risk and SHOULD be used carefully.


```text

```

```text
        ↓

        ↓
```

# 53. Forbidden Agent Capabilities

Unless a separately approved elevated policy explicitly permits otherwise, an agent MUST NOT autonomously:

- add signers;
- remove signers;
- lower threshold;
- replace recovery authorities;
- upgrade the account;
- increase its own spending limit;
- expand its own allowlist;
- alter its own permissions;
- delegate its authority;
- disable security policies.

---

# 54. Example Agent Delegation

Treasury:


# 79. Complete Illustrative Lithic Contract

The following is specification-oriented Lithic pseudocode. Exact compiler syntax may evolve while the normative behavior remains unchanged.

```lithic
requires TOKEN_TRANSFER
requires AI_CALL

contract LEP10015MultiSig {

    struct Signer {
        id: bytes32;
        signer_type: u8;
        scheme: u8;
        verifier: address;
        key_hash: bytes32;
        active: bool;
    }

    struct Call {
        target: address;
        value: u256;
        data: bytes;
        operation: u8;
    }

    struct Proposal {
        tx_id: bytes32;
        nonce: u256;
        proposer: bytes32;

        calls: Vec<Call>;

        valid_after: u64;
        valid_until: u64;

        policy_hash: bytes32;
        metadata_hash: bytes32;

        approval_count: u32;

        executed: bool;
        cancelled: bool;
    }

    state {
        signers: mapping<bytes32 => Signer>;
        approvals: mapping<bytes32 => mapping<bytes32 => bool>>;
        proposals: mapping<bytes32 => Proposal>;

        signer_count: u32;
        threshold: u32;

        next_nonce: u256;
    }

    init(
        initial_signers: Vec<Signer>,
        initial_threshold: u32
    ) {
        assert(initial_threshold > 0);
        assert(initial_threshold <= initial_signers.length);

        for signer in initial_signers {
            assert(!signers[signer.id].active);

            signers[signer.id] = signer;
        }

        signer_count = initial_signers.length;
        threshold = initial_threshold;
        next_nonce = 0;

        emit AccountInitialized(
            self.address,
            threshold,
            signer_count
        );
    }

    public fn propose(
        calls: Vec<Call>,
        valid_after: u64,
        valid_until: u64,
        policy_hash: bytes32,
        metadata_hash: bytes32
    ) -> bytes32 {

        let signer_id = resolve_signer(msg.sender);

        require(signers[signer_id].active);

        let nonce = next_nonce;
        next_nonce += 1;

        let tx_id = hash_transaction(
            self.address,
            chain.id,
            nonce,
            calls,
            valid_after,
            valid_until,
            policy_hash,
            metadata_hash
        );

        proposals[tx_id] = Proposal {
            tx_id: tx_id,
            nonce: nonce,
            proposer: signer_id,
            calls: calls,
            valid_after: valid_after,
            valid_until: valid_until,
            policy_hash: policy_hash,
            metadata_hash: metadata_hash,
            approval_count: 0,
            executed: false,
            cancelled: false
        };

        emit ProposalCreated(
            tx_id,
            signer_id,
            nonce
        );

        return tx_id;
    }

    public fn approve(tx_id: bytes32) {

        let signer_id = resolve_signer(msg.sender);

        require(signers[signer_id].active);

        let proposal = proposals[tx_id];

        require(!proposal.executed);
        require(!proposal.cancelled);
        require(block.timestamp <= proposal.valid_until);
        require(!approvals[tx_id][signer_id]);

        approvals[tx_id][signer_id] = true;
        proposals[tx_id].approval_count += 1;

        emit ApprovalAdded(
            tx_id,
            signer_id,
            proposals[tx_id].approval_count
        );

        if proposals[tx_id].approval_count >= threshold {
            emit ThresholdReached(tx_id);
        }
    }

    public fn revoke_approval(tx_id: bytes32) {

        let signer_id = resolve_signer(msg.sender);

        require(approvals[tx_id][signer_id]);
        require(!proposals[tx_id].executed);

        approvals[tx_id][signer_id] = false;
        proposals[tx_id].approval_count -= 1;

        emit ApprovalRevoked(
            tx_id,
            signer_id,
            proposals[tx_id].approval_count
        );
    }

    public fn execute(tx_id: bytes32) {

        let proposal = proposals[tx_id];

        require(!proposal.executed);
        require(!proposal.cancelled);

        require(
            proposal.approval_count >= threshold
        );

        require(
            block.timestamp >= proposal.valid_after
        );

        require(
            block.timestamp <= proposal.valid_until
        );

        verify_policy(proposal);

        // Effects before interactions.
        proposals[tx_id].executed = true;

        for call in proposal.calls {
            execute_call(call);
        }

        emit TransactionExecuted(
            tx_id,
            msg.sender
        );
    }

    public fn cancel(tx_id: bytes32) {

        require(msg.sender == self.address);

        require(!proposals[tx_id].executed);

        proposals[tx_id].cancelled = true;

        emit TransactionCancelled(tx_id);
    }
}
```

# 92. Determinism Rules

Consensus-affecting LEP100-15 operations MUST be deterministic.

AI inference itself MUST NOT be executed independently by validators in a manner that causes different validators to derive different results.

AI results entering contract state MUST arrive through the defined LEP100 AI-provider / fulfillment process.

Contracts SHOULD store:

```text
receipt
hash
proof
signed provider output
```

rather than rerunning nondeterministic inference during consensus execution.

# 94. Security Considerations

## 94.1 Signature Replay

Every signature MUST be bound to:

```text
chain
account
nonce
transaction content
version
```

---

## 94.2 Cross-Chain Replay

A signature created for chain 9005 MUST NOT automatically authorize the same transaction on another chain.

---

## 94.3 Duplicate Signatures

One signer MUST NOT count multiple times toward a threshold.

---

## 94.4 Signature Malleability

Signature-verification modules MUST reject non-canonical signatures where the selected signature algorithm has malleability concerns.

---

## 94.5 Reentrancy

External calls MUST NOT allow an executed transaction to be replayed through reentrancy.

---

## 94.6 Arbitrary Delegate Calls

Delegate execution presents substantial risk.

It SHOULD be disabled by default.

---

## 94.7 Signer Removal

The contract MUST enforce threshold invariants after signer changes.

---

## 94.8 Compromised Signer

Implementations SHOULD permit atomic signer replacement.

---

## 94.9 Malicious Proposal Metadata

Wallets MUST decode actual call data.

Display metadata MUST NOT replace decoded transaction data.

---

## 94.10 Blind Signing

Wallets SHOULD provide human-readable transaction interpretation.

Unknown calldata SHOULD generate a prominent warning.

---

# 95. AI-Specific Security

## 95.1 Prompt Injection

Untrusted transaction metadata, token names, websites and contract strings may contain adversarial instructions.

AI security systems MUST treat blockchain content as untrusted data.

---

## 95.2 Hallucinated Transaction Meaning

An AI explanation MAY be incorrect.

Users MUST be able to inspect deterministic decoded transaction details.

---

## 95.3 Model Compromise

Account security MUST NOT rely solely on one model provider.

High-value accounts SHOULD use:

```text
human threshold
+
deterministic policy
+
AI advisory
```

rather than:

```text
AI alone
```

---

## 95.4 Stale Assessment

Every assessment MUST contain an expiry.

An expired assessment MUST NOT satisfy a required AI policy.

---

## 95.5 Transaction Binding

AI analysis MUST be bound to the exact transaction hash.

Changing:

```text
recipient
amount
target
calldata
nonce
```

creates a different transaction requiring a new assessment.

---

## 95.6 Agent Key Compromise

Agent keys should be treated as potentially hot credentials.

Their authority SHOULD therefore be substantially narrower than owner authority.

---

## 95.7 Self-Escalation

An agent MUST NOT be able to modify the policy controlling that same agent without normal multisig authorization.

---

## 95.8 AI Provider Availability

Accounts using mandatory AI checks MUST define an outage procedure.

# 108. Rationale

Multisignature authorization belongs at the account layer rather than the token layer.

This permits one LEP100-15 account to control:

```text

NFTs

validator funds
protocol contracts
treasuries
bridges
DEX administration
DAOs
AI agents
Web4 applications
```

without creating separate multisig logic for every asset standard.

---

# 109. AI Rationale

Web4 applications will increasingly involve machine participants.

Prohibiting agents entirely would force developers to build incompatible proprietary automation systems around multisig accounts.

LEP100-15 instead standardizes bounded machine authority.

The design therefore separates:

```text
Intelligence
Authorization
Execution
```

AI provides intelligence.

Cryptography provides authorization.

LithoVM provides deterministic execution.
